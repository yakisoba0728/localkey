목표: YubiKey 5C Nano / 5.7.4의 외부 동작과 호스트 호환성을 구현·검증합니다.
goal은 활성 상태입니다. 완전 동일 구현으로 판정하지 않았습니다.
완료 기준과 남은 차이는 compatibility-matrix.json과 implementation-status.json에 있습니다.

이번 버전의 검증 추가: 읽지 않은 CCID 응답·승인 대기 중 실제 USB 구성 전환

  no-NIC ARM64 Linux 6.8.0-146-generic/dummy_hcd의 자체 시험 장치에서 원래0.37
  구현을 먼저 검증했습니다. 네 경우의 79항목과 확대 CID 라우팅 86항목을 통과했습니다.
  두 stock SDK 수신기가 동시에 같은 HID 리포트를 읽는 확대 검사의 Wrong channel
  실패 61항목도 원본 보고서·콘솔·helper로 보존했습니다. 이 실패를 장치 소스 수정의
  근거로 사용하지 않았습니다. USB backend·Linux·macOS·카드 코어는 동결한0.37과
  바이트가 같고, 버전 메타데이터와 정식 검증·결과·포장 게이트를 추가했습니다.

  실제0.38 전체 Linux 실행에서 커널에 저장됐지만 읽지 않은19바이트 HOTP,
  먼저 저장한 슬롯 응답으로 차단한19바이트 쓰기, 원래64바이트 PIV 응답 뒤의 ZLP,
  실제 stdin 터치 승인을 기다리는 요청을 각각 유지한 채 native FIDO Management로
  FIDO+CCID profile6에서 FIDO 전용 profile2로 변경하고 복원했습니다. 8회 구성 전환과
  초기 전환을 포함한9회 재열거, 같은 세 서비스와 기존 자격 증명 유지, 새 세대에서
  이전 CCID worker 부재, 이전 handle의 실제 ENODEV19, 새 PowerOn·SDK 회복을
  검증했습니다. worker 부재 관찰만으로 재열거 전 정확한 join 시각을 주장하지 않습니다.

  승인을 기다리는 카드 요청이 설정 트랜잭션을 막는 동안 두 번째 CID의 실제
  GetInfo CHANNEL_BUSY6과 PING을 확인했습니다. 변경하지 않은64바이트 실제 HID
  리포트를 한 hidraw FD에서 CID별로 전달하는 시험용 호스트 라우터를 사용했습니다.
  BUSY 자동 재시도를 피하기 위해 stock SDK의 변경하지 않은 단일 transaction
  메서드를 호출했습니다. 서로 독립된 stock SDK 프로세스의 동시 동작을 입증한 것은
  아닙니다. 실제 USB controlABORT와 원래sequence의 bulkABORT 후 설정이 완료됐고,
  원래 터치 요청은 HOTP를 소비하지 않았습니다. 복원 후 새 실제 승인이 필요합니다.

  원래 자격 증명의 독립 PIN/UV protocol2 서명9개와 단조 증가 카운터를 검증했습니다.
  OATH HOTP는 독립 HMAC과 비교하며 일반 카운터6·터치 카운터1을 확인했습니다.
  설정과 OTP 내부 sequence 외의 카드 평문 상태는 두 전환을 거쳐 보존됩니다.
  50바이트 PIV 객체는 불투명 전송 fixture이며 유효한 CHUID로 취급하지 않습니다.
  읽지 않은 응답의 reboot 유예는 사설 소프트웨어 모델이고 실제 키의 타이밍은
  측정하지 않았습니다. 카드 자동 승인은 없고 FIDO 자동 승인은 자체 fixture 전용입니다.

  기존5841개 소스·프로토콜 회귀,205개 실제 CCID 복귀 검사와 OS·브라우저 검증을
  다시 실행했습니다. 완전 동일 판정은 하지 않았습니다. macOS 권한 서명·실제 장치
  등록, 생산 UDC·다른 구성·긴 메시지 경합·실제 firmware 차등 검증은 남아 있습니다.

0.37 구현·검증과 이전 기록

소프트웨어 보안키 에뮬레이터 0.37.0

목표: YubiKey 5C Nano / 5.7.4의 외부 동작과 호스트 호환성을 구현·검증합니다.
goal은 활성 상태입니다. 현재는 완전 동일 구현으로 판정하지 않았습니다.
완료 기준과 남은 차이는 compatibility-matrix.json과 implementation-status.json에 있습니다.

swpasskey MIT 소스를 확장한 C++ FIDO 코어와 새 Python 스마트카드·OTP 코어입니다.
새 키를 생성하고 서비스에 별도 등록합니다. 기존 실제 키의 비밀키·PIN·자격 증명은
복사하거나 변경하지 않았습니다. 기준 키에서는 INIT/GetInfo와 공개 USB 메타데이터,
OpenPGP 공개 기능 정보를 읽었습니다. USB 설정·HID 리포트 수집은 IORegistry/캐시를
사용하며 USB 장치를 열거나 리셋·설정하지 않았습니다. 이번 OpenPGP 관찰은 시스템
PC/SC의 shared 연결로 SELECT·GET VERSION·허용 목록 GET DATA만 수행하고
LEAVE_CARD로 종료했습니다. 공개 알고리즘 FA와 보안 지원 7A도 읽었습니다.
PIN 시도·쓰기·활성화·초기화는 없었습니다. 임시 앱 선택은 바뀌었으며 실제 serial·
지문·cardholder·서명 카운터 payload는 보고서에서 폐기했습니다. 공개 증명 템플릿
FC에서는 firmware 확장의 DER 태그/길이만 확인하고 인증서 원문·serial·subject·
공개 키·날짜·확장 값은 저장하지 않았습니다.

이번 버전의 구현·검증 추가: 실제 USB 복귀 후 CCID 카드 전원·인증 수명

  USB CCID Rev1.1 3.3·6.3.1의 복귀 모델을 구현했습니다. FunctionFS의 실제
  SUSPEND/RESUME 이벤트를 처리하고, 복귀 후 점유 슬롯을 비활성 상태1·정지 클록3으로
  보고합니다. 삽입 알림 5003을 한 번 보내며 새 IccPowerOn 전에는 APDU를 거절합니다.
  명시적 PowerOn 후 기존 ATR과 활성 상태0·동작 클록0을 받습니다. 0.36의 실제
  31항목 뒤 활성 상태0 실패 기록·콘솔·원본 관찰 보고서는 별도로 그대로 보존했습니다.

  카드 세션만 종료하므로 이미 확정한 응답은 기존 USB 세대·주소·sequence와 함께
  유지됩니다. 기존 전송 스레드·fd·버퍼에서 대기 중인 HOTP 응답 세 개와 ZLP,
  커널에 먼저 저장된 슬롯 응답 세 개와 별도 19바이트 HOTP 응답을 검사했습니다.
  커널 write 진입·종료 기록으로 먼저 완료된 쓰기를 입증하고, 읽지 않은 원본을
  실제 절전·복귀 후 받아 독립 HMAC과 단일 HOTP 증가를 검증했습니다. 커널 FIFO에
  저장된 응답의 write 완료를 응답 유실로 판정하지 않습니다. 시험용 불투명 50바이트
  PIV 객체는 유효한 CHUID가 아닙니다. 일반 READ 뒤 암호문 변경은 평문 상태로 비교합니다.

  PIV PIN·관리자 인증은 복귀 후 해제되고, 새 PIN 확인 후 같은 영구 키로 서명합니다.
  실제 stdin 승인을 기다리던 HOTP는 CMD_ABORTED로 끝나며 카운터·저장 바이트는
  변경하지 않습니다. 새 요청은 새 실제 승인을 받아야 하고 결과·단일 증가를 독립
  HMAC으로 검증합니다. 이 카드 서비스에는 --testing을 사용하지 않았습니다.
  FIDO 시험의 자동 승인은 자체 시험 장치에만 적용하며 물리 터치를 뜻하지 않습니다.

  no-NIC ARM64 Linux 6.8.0-146-generic/dummy_hcd의 기준과 같은 FIDO+CCID 구성에서
  여섯 번의 실제 runtime PM과 205항목, 원래 자격 증명의 일곱 독립 PIN/UV protocol2
  서명을 검증했습니다. 원래 세 서비스·주소·설정·HID 드라이버는 유지됩니다.
  실제 삽입 알림은 초기 한 개와 복귀 여섯 개이고 추가 알림이 없음을 확인합니다.
  Linux Endpoint 클래스는 동결한0.33과 바이트가 같지만 카드 복귀 처리가 추가된
  전체 USB 소스·bridge 바이너리는 다릅니다. 두 사실을 별도 보고서로 구분합니다.

  macOS IOUSBHost PortSuspend/PortResume도 같은 카드 처리를 호출하며, 처리 완료 후
  명령에 응답하도록 구현·컴파일했습니다. 공통 --wire-test는 중복 복귀의 무효성,
  슬롯 전원·인증 해제·원래 PIV/FIDO 서명 등을 13개 추가 검사로 확인했습니다.
  이 결과는 macOS의 권한을 갖춘 실제 장치 등록·복귀 시험을 대신하지 않습니다.
  GadgetFS 복귀, 다른 USB 구성·UDC, 전체 메시지 경합·원격 깨우기·플랫폼 수면과
  실제 유비키의 전력·타이밍·토큰 차등 검사는 아직 미검증입니다. goal은 활성 상태이고
  완전 동일 판정은 하지 않았습니다.

0.36의 중단 관찰 보정 기록

  당시 전체 실행에서 신호 전달만 관찰하고 대응 write 종료를 찾지 못한 실패를
  보존했습니다. 원래 CCID 읽기 전 중지했으므로 응답 유실로 판정하지 않았습니다.
  원래 쓰기 전에 추적을 켜 실제 fd·버퍼·길이 진입 후 EINTR·신호 쌍을 확인하는
  보정은 유지하며 현재 새 전체 게스트에서도 113항목·12쌍을 검증합니다.
  근거: linux-usb-interrupt-prior-v36-trace-arm-failure.json,
  usb-interrupt-trace-arm-observation.json. 원래 Endpoint 쓰기 로직은 같습니다.

0.35의 검증 추가: 실제 Linux USB 자동 절전과 SDK 접근에 의한 복귀

  연결된 기준 키에서 저장한 것과 같은 FIDO+CCID USB 설정을 실제 Linux에 등록하고
  USBDEVFS_ALLOW_SUSPEND, 커널 runtime_status와 절전 시간, 실제 rpm 반환값 및
  usb_runtime_suspend/resume 추적을 검증합니다. 수동 on, native FIDO SDK 접근,
  native CCID/OATH SDK 접근으로 복귀하는 세 번의 실제 주기가 52항목을 통과했습니다.
  같은 USB 주소·설정·HID 드라이버·서비스 세 개를 유지하며, 절전 중 저장 파일은
  그대로입니다. 복귀 후 네 번의 독립 PIN/UV 서명과 HOTP 0→1 단일 증가를 확인했습니다.

  OTP 키보드가 포함된 기본 7번 설정이 자동 절전되지 않던 원인도 확인했습니다.
  사용 횟수는 0이지만 실제 커널은 remote wakeup needed for autosuspend를 기록하고
  autosuspend_check는 EOPNOTSUPP, 장치 runtime suspend는 EAGAIN을 반환합니다.
  절전을 강제로 성립시키기 위해 USB 설정 바이트나 HID 드라이버를 변경하지 않았습니다.
  전송 코어는 0.33 구현과 같습니다. 이번 변경은 검증 범위와 근거의 추가입니다.

  이 결과는 격리된 Linux 6.8.0-146-generic의 dummy_hcd에서 관찰한 6번 구성의
  실제 runtime PM입니다. 다른 구성의 runtime PM, 더 넓은 동시 전송·취소·설정 변경, 원격 깨우기,
  전체 플랫폼 수면과 실제 하드웨어의 전력·타이밍·PIN 토큰 동작은 아직 미검증입니다.
  보고서: linux-usb-runtime-result.json, usb-runtime-power-observation.json.

  전체 시험에서 기존 중단 검사가 write 종료 이벤트만 기다리고 곧바로 신호 전달을
  판정하는 경합도 발견했습니다. 실제 EINTR은 이미 관찰됐습니다. 데이터와 ZLP
  모두 두 이벤트의 수를 함께 기다리도록 검사를 수정했고, 원본 실패 기록은
  linux-usb-interrupt-prior-v35-trace-failure.json에 보존했습니다.

  새 runtime 보고서에 이전 dmesg가 포함되어 호스트 검증이 재설정 문구를 두 번
  세는 문제도 수정했습니다. 해당 시험 구간의 실제 커널 로그 행 네 개를 검증하며,
  원본 실행 종료0·게스트 종료0과 동일 console SHA-256을 보존해 다시 판정했습니다.
  linux-native-host-gate-observation.json과 linux-native-prior-v35-host-console.txt에
  당시 원본 실패·재검증 범위를 보존했습니다. 0.36은 새 전체 게스트 실행입니다.

0.34의 검증 추가: 연결 유지 중 응답 데이터·종료 패킷 중단 복구

  실제 Linux 커널에서 CCID 응답을 보내는 스레드만 식별해 SIGUSR1을 전달합니다.
  프로세스 그룹·엔드포인트 파일·실제 write 호출·버퍼를 확인하며 실제 커널의
  write EINTR와 signal_deliver 기록을 함께 검증합니다. 전송 중단 12회를 포함한
  113항목이 같은 USB 주소·설정·서비스 세 개를 유지하면서 통과했습니다.
  HOTP 응답 세 개는 각각 세 번 중단한 뒤 원래 순서와 값으로 수신했으며,
  독립 HMAC과 0→1→2→3 단일 카운터 증가, 다음 SDK 요청의 무중복을 확인했습니다.

  별도로 64바이트 PIV 객체 응답을 받은 뒤 종료용 ZLP만 세 번 중단합니다.
  다시 받는 것은 0바이트 종료 패킷이며 이전 데이터가 재전송되지 않습니다.
  다음 PIV SDK 요청의 새 순서와 원본 객체, FIDO GetInfo·PING 격리와 다섯 독립
  PIN/UV 서명·OTP HMAC도 검증합니다. 중단 재시도 동안 저장 파일은 그대로이며,
  다음 일반 PIV 읽기 트랜잭션의 재암호화 이후에도 저장된 논리 상태는 같습니다.

  보존된 원본 0.32는 데이터와 ZLP 모두 실제 USB 시간 초과로 실패했습니다.
  각각 동일한 검증 소스에서 0.33의 성공도 확인했습니다. 이번 검증은 이미 0.33에서
  수정한 전송 보존 로직을 확인하며, USB 브리지 바이너리와 해당 로직은 동일합니다.
  linux-usb-interrupt-result.json과 usb-interrupt-recovery-observation.json에 근거가 있습니다.
  실제 키·일반 UDC·다른 오류와 경합·전기적 타이밍까지 검증한 것은 아닙니다.

이전 v0.23 허용 목록 변경

  허용 목록이 마지막 OCE serial만 검사하던 동작을 수정했습니다. Yubico CLI의
  체인 전체 규칙에 따라 제시된 root·중간·leaf 각각의 serial을 검사합니다.
  유효한 조각이라도 serial이 없으면 즉시 거부하며 한 CA의 목록이 전체 체인을
  허용해야 합니다. 여러 CA 목록을 합쳐서 인증할 수 없습니다.
  wildcard 후보를 조각마다 유지하고, 첫 명시 CA의 정책은 후속 참조로 바뀌지 않습니다.
  제출하지 않은 optional root나 저장된 CA 인증서의 serial은 요구하지 않습니다.
  허용 serial도 서명/역할 검증을 건너뛰지 않으며 ASN.1 부호 padding도 검증합니다.
  거부는 기존 OCE를 지우지만 retry·암호화 저장소·다른 보호 채널을 바꾸지 않습니다.
  peer의 subset 정책 commit 실패는 기존 목록/캐시를 보존하며 성공하면 캐시를
  무효화합니다. clearlist·restart·정책 복구·SDK a/c receipt/KDF/R-MAC도 검증했습니다.
  소켓/직접 IFD 검사 81개씩 통과합니다. 기존 최종 v0.22 ZIP은 첫 누락 root를
  받아 같은 새 검사에서 실패합니다. 기존 정상 fixture도 전체 serial 목록으로 수정했습니다.
  출처: https://docs.yubico.com/software/yubikey/tools/ykman/Security_Domain_SD_Commands.html
  즉시 거부 시점은 소프트웨어 모델입니다. 실제 serial 범위·오류 코드·펌웨어 타이밍은
  아직 미측정이며 GP 일반 규칙을 Yubico 동작으로 대신하지 않았습니다.
  실제 키에 접근하지 않았습니다. goal은 활성이고 완전 동일 판정은 아직 아닙니다.

이전 평문 명령·SELECT 권한 종료 수정

  Yubico 문서의 평문 명령 종료 규칙에 맞춰 기존 핸드셰이크 예외를 수정했습니다.

  암호화된 PSO와 정상 보호 핸드셰이크는 유지하며 SDK 복구도 검증했습니다.

  소켓/직접 IFD에서 새 경계 검사 394개씩 통과합니다. 기존 v0.21 ZIP은
  첫 평문 PSO를 통과시키므로 같은 새 검사에서 실패하는 것을 확인했습니다.
  기존 PSO 검사는 보호 전송 61개씩으로 수정하여 캐시 검사가 전송 거부에
  가려지지 않도록 했습니다. 공유 reset의 캐시 연결과 활성 전송 연결도 분리합니다.

  실제 오류 코드와 핸드셰이크 예외는 미측정입니다. 소프트웨어6982 모델입니다.
  GP의 CCT는 새 LOAD/INSTALL 콘텐츠 범위이며 기존 키/데이터 수정의 rollback이
  아닙니다. Yubico 적용 여부를 먼저 확인해야 합니다. SubjectID 비교 대상도
  INSTALL의 Application Provider Identifier이며 SD 인증서 subject/CPLC가 아닙니다.
  실제 키에는 접근하지 않았습니다. 실제 OS 통합·펌웨어 차이 검증이 남습니다.

이전 인증서 조각 검증 구현 (v0.22의 보호 전송 규칙 적용)

  잘못된 중간 인증서를 마지막 leaf까지 받기 전에는 통과시키던 PSO를 수정했습니다.
  매 조각에서 서명·역할·공개 키·CA/keyCertSign·누적 path-length와 기존
  날짜/critical 제약 모델을 검증합니다. 불완전 체인은 OCE 권한을 만들지 않습니다.
  첫 PSO의 CA 참조가 체인을 결정하며 후속 P1/P2 참조는 무시합니다.
  wildcard의 첫 일치 CA에 고정하지 않고 제시된 모든 조각/최종 serial 허용 판단까지 후보를 유지합니다.
  protected PSO는 기존 채널과 PIV PIN 확인 상태를 유지합니다. 평문은 위 규칙을 따릅니다.
  거부된 조각은 체인/캐시를 지우며 암호화 저장소와 기존 채널을 보존합니다.
  잘못된 DER는 최초 CA의 모델 retry만 소비하고 중복 확장은 malformed로 처리합니다.
  자체 정상 root/중간/직접 leaf와 policy-free 체인의 SDK receipt/KDF/MAC,
  보호 PSO 전후 PIV 서명을 독립 검증했습니다. 실제 MUT 전환은 이전 PIN을 지웁니다.
  소켓과 직접 IFD에서 새 자체 키만 사용했습니다. 실제 키에 접근하지 않았습니다.
  기존 모델6982를 유지합니다. 실제 거부 코드와 GP6600, 날짜/qualifier/한도의
  펌웨어 허용 범위·체인 serial 허용 규칙·확정 GP1.4는 미비교입니다.
  SD transaction·critical SubjectID·실제 OS 연동도 남아 있으며 goal은 활성입니다.

이전 버전의 보호 핸드셰이크·단일 c 세션 모델

  성공한 보호 SCP11a/b/c 핸드셰이크 뒤 새 채널을 잃던 오류를 수정했습니다.

  receipt/KDF·응답 복호화/MAC·기존 채널 거부를 확인했습니다.
  SDK reset의 내부 잘못된 인증과 미완료 SCP03 INIT 경로는 유지합니다.
  공유 SD에서는 성공적으로 저장된 최신 c 세션이 이전 c 세션을 대체하는
  모델을 구현했습니다. c 토큰과 키 상태가 함께 commit/rollback되며
  평문/보호 핸드셰이크 저장 실패나 잘못된 요청은 다른 연결을 종료하지 않습니다.
  다른 연결의03/a/b, SELECT·연결 종료·새 세션·키/앱 보존을 검사했습니다.
  GP의 단일 영속 OCE 규칙은 i-byte1 bit3이 켜졌을 때 적용합니다.
  실제 공개 option9b06은 이 비트가 꺼져 임시 OCE만 표시하므로,
  이전 문서의 전역 단일 영속 캐시를 필수 구현 대상으로 보던 표현을 정정합니다.
  임시 OCE와 실제 논리 채널 범위는 계속 대조해야 합니다.
  자체 새 키만 사용하며 소켓과 별도 직접 IFD에서 검증했습니다.
  최신 c가 이전 c를 대체하는 정책/상태 코드·실패한 MUT의 이전 채널 수명은
  물리 펌웨어와 미비교입니다. SD transaction·확정 GP1.4·실제 OS 연동도 남습니다.

이전 버전의 공유 Domain 정책·초기화·저장 실패 복구

  v0.18에서 재현한 서로 다른 클라이언트의 오래된 OCE 캐시 오류를 수정했습니다.
  성공한 허용 목록 변경은 연결별 캐시와 업로드 중인 체인을 무효화합니다.
  같은 값·목록 삭제·다른 CA·c counter 변경을 모두 검사했습니다.
  내부 세대값은 정책과 함께 저장하며 거부/저장 실패 시 함께 복구합니다.
  이미 열린 SCP03/a/c 채널은 일반 정책 변경 이후에도 계속 동작합니다.
  CA 공개 키 교체는 이전에 검증한 OCE를 유지하되 새 PSO는 새 CA로 검사합니다.
  공유 Domain 초기화는 다른 연결의 이전 채널과 캐시를 종료합니다.
  같은 자체 SD 키를 다시 넣어도 초기화 전 캐시는 사용할 수 없습니다.
  초기화 저장 실패에서는 다른 연결의 채널/캐시와 키·정책·식별자를 보존합니다.
  이전 상태의 키·인증서·재시도·CPLC를 바꾸지 않고 누락된 내부 필드만 추가합니다.
  변경하지 않은 SDK의 receipt/KDF/암호화/MAC을 소켓과 별도 직접 IFD에서
  확인했습니다. 자체 새 소프트웨어 키만 사용하며 실제 키에 접근하지 않았습니다.
  GP 공개 검토본의 수명 주기 모델입니다. v0.20은 보호 핸드셰이크와 단일 c
  모델을 추가했습니다. 임시 OCE·SD transaction·확정 GP1.4·실제 논리 채널과
  OS 연결은 계속 대조해야 합니다. 전역 단일 영속 OCE 표현은 위에서 정정했습니다.

이전 버전의 SCP11c 키 교환·명령 제한·카운터

  SCP11c의 SD 측 키 교환을 정적 키로 수정했습니다. 응답 5F49도 자체 SD
  정적 공개 키를 반환하며 SCP11a/b는 새 임시 키를 계속 사용합니다.
  ECDH·SHA256 counter KDF·receipt CMAC를 독립 계산하고 SDK의 암호화·MAC을
  확인했습니다. 같은 자체 요청을 재전송하면 c의 응답은 같고 a/b는 달라집니다.
  c 채널의 PUT KEY·키 DELETE·SET STATUS를 모델 6985로 거부합니다.
  기존 검사도 c의 잘못된 키 가져오기 성공 기대에서 실제 제한 검사로 바꿨습니다.
  Yubico Android/.NET의 공개 시험 코드도 c의 키 삭제 실패를 요구합니다.
  SCP11c 허용 목록에는 tag92의 2바이트 양수 카운터 1..32767을 요구하고,
  비-c 채널에서는 이 필드를 거부합니다. 각 CA의 카운터가 엄격히 증가하며
  목록 삭제·다른 SCP 쓰기·CA 교체·재시작으로 카운터를 되돌리지 않습니다.
  자체 c 세션에서 같은 키·유효한 MAC의 관리 패킷을 다시 보내면 카운터가
  거부합니다. 요청 MAC과 거부 응답 MAC을 독립 계산해 검증했습니다.
  실패한 입력은 카운터를 소비하지 않습니다. 제어된 저장 실패에서는 목록과
  카운터의 디스크·메모리 상태를 함께 복구하고, 이전 채널을 종료합니다.
  소켓과 직접 IFD에서 새 자체 키만 사용했고 실제 키에는 접근하지 않았습니다.
  GP1.3.0.13 공개 검토본 모델입니다. 확정 GP1.4·실제 펌웨어 상태/시간 특성,
  SD content transaction·동시 c 세션·proprietary GENERATE 정책은 남아 있습니다.
  당시 재현한 공유 허용 목록과 다른 연결의 OCE 캐시 문제는 v0.19에서 수정했습니다.
  shared-domain-observation.json은 v0.18의 역사적 자체 재현 기록이며
  현재 검증은 domain-shared-result.json / ifd-domain-shared-result.json에 있습니다.

이전 버전의 SCP11 OCE 캐시·체인·허용 목록 수명 주기

  누락·불완전·무효 캐시는 MUTUAL AUTHENTICATE에서 모델 6985를 반환합니다.
  기존 암호화 채널은 유지하며 거부된 목록 업데이트는 캐시와 데이터를 유지합니다.
  완료된 PSO 체인을 다음 체인의 접두부로 붙이던 오류를 수정했습니다.
  새로운 완전한 체인이 호스트를 교체하고 새 불완전 체인은 이전 권한을 사용하지 못합니다.

  변경하지 않았으며, 분리된 시험 단계에서 이미 보낸 PSO만 생략했습니다.
  SDK가 MUT 요청·ECDH receipt·세션 KDF·암호화 응답 MAC을 검증합니다.
  이 lifecycle/6985는 GP1.3.0.13 공개 검토본 모델이며 GP1.4 확정본과
  실제 5.7.4 상태·시간 특성은 미검증입니다. 이번 버전은 실제 키에 접근하지 않았습니다.
  남은 체인 serial 허용 규칙·중간 PSO 즉시 검증·critical Subject ID·30초
  캐시 제한은 계속 점검해야 합니다. v0.18은 당시 남았던 c의 정적 SD ECDH,
  key-command 제한과 tag92 counter를 소프트웨어 모델로 구현·검증했습니다.

이전 버전의 SCP03 전체 버전 범위

  SCP03의 사용자 키 버전을 공개 Yubico 문서의 1..254에 맞췄습니다.
  공장 기본값 255와 사용자 버전 0은 거부합니다. 이전에는 SCP11의
  7비트 범위를 SCP03에도 적용하여 정상적인 128..254를 거부했습니다.
  각 버전마다 새로운 소프트웨어 AES 키를 넣고 SDK의 KCV와 키 열거를
  확인했습니다. 모든 254개 버전에서 INIT UPDATE 헤더와 AES-CMAC
  카드 암호문을 독립 재계산하고 SDK 인증·응답 복호화·MAC을 검증했습니다.
  INIT UPDATE는 측정된 공개 지원 정보와 같은 option 60을 반환합니다.
  SDK가 무시하던 이 필드의 기존 00 값을 수정했습니다. 실제 카드의
  초기화 응답이나 128/254 경계 인증·거부 코드는 측정하지 않았습니다.
  127/128/254 재시작, 3세트 용량, 상위 버전 교체·삭제·wildcard·
  차단 항목 선택과 mixed-version SDK 초기화를 양쪽 전송에서 검사했습니다.
  SCP11의 사용자 버전은 별도 1..127 프로파일을 유지합니다. private/public
  키 생성·가져오기의 0/128/255 거부와 127의 SDK key agreement도 확인했습니다.
  이 버전은 새 자체 소프트웨어 키만 사용하며 실제 키에 접근하지 않았습니다.

이전 버전의 Security Domain 공개 메타데이터·초기화 프로파일

  Security Domain의 SELECT 25바이트와 GET DATA 0066 63바이트를
  실제 5.7.4 키의 공개 응답과 동일하게 맞췄습니다. 고정 SELECT·GET DATA를

  동작을 구현했습니다. 기존 채널로 마지막 응답 MAC을 반환한 뒤 인증을 종료합니다.

  소프트웨어 한도로 적용했습니다. 이름은 39바이트, 언어는 최대 8바이트의
  쌍, 성별은 ASCII 값, 지문은 20바이트, 생성 시간은 4바이트입니다.
  Private Use 101/103 쓰기는 PW1의 82 확인이 필요하며 서명용 81만으로
  허용하지 않습니다. 102/104 쓰기와 104 읽기는 관리자 83을 요구합니다.
  읽기 전용·미지원 객체 쓰기와 Resetting Code 읽기를 거부합니다.
  네 인증서 슬롯의 한도·빈 PUT 삭제·재시작, oversized 교체 실패 시 불변성,
  기존 큰 객체의 읽기 보존과 작은 값 교체·삭제로 복구를 확인했습니다.
  socket과 네이티브 IFD 직접 ABI에서 독립 SDK·암호 검증이 통과했습니다.
  실제 키의 공개 메타데이터만 비교했습니다. 실제 키에 저장/PIN/challenge/
  암호 명령을 시험하지 않았으므로 정확한 쓰기 거부 status·할당 오버헤드·
  내용 허용 범위·aggregate PUT·증명 reset lifecycle·터치 타이밍은 남아 있습니다.

이전 버전에서 검증한 OATH 프로파일

  OATH PUT의 초기 카운터 IMF를 HOTP 전용 4바이트로 검사합니다.
  중복 property·누락/중복/알 수 없는 TLV와 명령 P1/P2·본문을 검사하며,
  없는 자격 증명 계산과 접근 코드 없는 VALIDATE는 문서의 0x6984를 반환합니다.
  SET CODE의 host challenge는 8바이트, SHA1 proof는 20바이트입니다.
  VALIDATE는 가변 challenge TLV를 처리하며 7/9바이트 응답을 독립 HMAC으로 확인했습니다.
  잘못된 SET CODE proof는 문서의 mismatch 0x6984를 반환하고 상태를 유지합니다.
  독립 SDK로 SHA1/256/512의 RFC6238 벡터 18개를 확인했습니다.
  HOTP 초기 카운터·재시작·full/truncated HMAC, CALCULATE ALL의 실제 값과
  HOTP/touch placeholder, 증가 전용 challenge 보존도 독립 계산과 대조했습니다.
  접근 코드의 자체 salt/PBKDF2와 상호 인증·제거를 확인했습니다.
  5.7 공식 문서의 64개 용량 모델은 65번째 거부, 꽉 찬 상태의 교체·이름 변경,
  삭제 후 새 등록과 재시작을 검증했습니다. 잠긴 OATH 앱 초기화는 salt를
  교체하고 OATH 데이터만 지우며, 자체 PIV F9 발급자를 유지합니다.
  잘못된 요청의 거부 status와 암호화 저장소 불변성을 함께 검사했습니다.
  socket/직접 IFD 경로의 소프트웨어 검증입니다. 실제 펌웨어의 malformed 입력
  허용 범위·검사 순서·최대 secret/challenge 길이·카운터 포화는 미비교입니다.

이전 버전에서 검증한 PIV 초기 프로파일

  PIV SELECT의 application template와 고정 Discovery AID/PIN policy를 반영했습니다.
  읽기 전용 Discovery·Biometric Information Group Template 쓰기를 거부하며,
  생체 기능이 없는 카드의 빈 BITGT와 초기 표준 객체를 독립 SDK로 확인했습니다.
  PIN/PUK 재시도 설정은 1~255회입니다. 오류 status word는 15에서 포화하지만
  metadata는 실제 8비트 횟수를 유지합니다. 255/200회 설정, 16→15→14 경계,
  성공 시 전체 횟수 복구, 잘못된 VERIFY 길이·재시도 설정의 불변성을 확인했습니다.
  자체 F9 키·인증서를 처음부터 준비합니다. F9의 EC P-256/P-384와
  RSA 2048/3072/4096 생성, EC/RSA 가져오기 및 교체한 키의 증명을 검증했습니다.
  증명은 발급자 subject·유효기간을 따르고, 자체 16바이트 무작위 인증서 serial과
  별도 카드 serial을 사용합니다. 제조사 CA·FIPS/CSPN 인증은 주장하지 않습니다.
  PIV 초기화와 재시작은 현재 F9 키·인증서를 유지합니다. 삭제한 인증서는
  되살리지 않습니다. 불일치·잘못된 DER 인증서는 opaque 객체로 보관하며,
  서명 검증 실패나 증명 오류가 이를 자동 교체하거나 상태를 변경하지 않습니다.
  이전 지연 생성 CA 상태를 읽을 때 기존 발급자와 사용자 키를 보존합니다.
  기존 사용자 키의 서명을 독립 검증하고, PIV 초기화 후에도 OATH 키와
  HOTP 카운터가 유지되는 것을 확인했습니다. 용량이 가득 차도 이미 준비된 F9로
  증명할 수 있습니다. 이 검사는 fresh socket과 네이티브 IFD 직접 ABI에서
  실행했으며, 실제 유비키의 초기 객체·거부 status와 차등 비교하지 않았습니다.

이전 버전에서 검증한 비상주 FIDO 동작

  새 소프트웨어 비상주 FIDO2/U2F 키를 저장소 항목에 보관하지 않습니다.
  ES256/Ed25519/ES384 키와 보호 정책을 자체 128바이트 암호화 ID에서 복원하며,
  RP 해시를 인증하여 다른 서비스와 변조된 ID의 사용을 거부합니다.
  저장소에는 공통 래핑 루트와 서명 카운터만 유지합니다. 초기화는 루트를
  없애 기존 ID를 무효화합니다. credRandom은 ID별로 UV/noUV 값을 분리해 유도합니다.
  10,001회 생성해도 항목 수와 초기화된 저장소 바이트가 늘지 않는 것을 확인했습니다.
  상주 100개가 가득 찬 상태에서도 새 비상주 FIDO2/U2F 등록이 동작합니다.
  독립 FIDO SDK로 세 알고리즘 서명, 재시작, hmac-secret, PIN 보호, U2F 교차 사용,
  excludeList와 초기화 뒤 무효화를 검증했습니다. 저장 실패 시 루트·카운터를 롤백하고
  32비트 카운터의 최대값에서 추가 UP 서명을 거부하여 0으로 돌아가지 않습니다.
  공식 문서의 상주 credBlob 설명에 맞춰 새 등록에서는 상주 키만 blob을 저장합니다.
  카운터와 비상주 credBlob의 실제 펌웨어 경계 응답은 아직 비교하지 않았습니다.
  암호화 저장소 v1/v2를 읽고 첫 변경에서 v3으로 옮깁니다. 기존 32바이트 ID와
  비상주 저장 항목의 개인키는 유지하며, 이전 버전의 writer는 v3을 거부합니다.
  하드웨어 백엔드의 기본 ES256 키는 기존 저장된 핸들 방식입니다.
  별도 래핑 형식을 사용하며 실제 유비키의 비밀키나 제조사 형식을 복제하지 않습니다.

이전 버전에서 검증한 USB·CCID·PIV 동작

  기준 키의 FIDO+CCID USB 설정 125바이트와 FIDO HID 리포트 34바이트를 읽었습니다.
  같은 인터페이스 조합에서 설정·리포트 바이트가 wire 모델과 일치합니다.
  FIDO OUT 04/IN 84, CCID OUT 02/IN 82/알림 83, 버스 전력 30mA,
  HID 1.10, CCID 메시지 3072바이트와 4000kHz/307200bps 프로파일을 반영했습니다.
  공개 USB bcdDevice 0x0574는 호환 프로파일입니다. GetInfo firmwareVersion은
  독립 소프트웨어 값 3이며, 제품 이름·일련번호·키·증명 신뢰도 별도입니다.
  OTP가 포함된 다른 USB 설정 조합은 실제 키와 아직 비교하지 않았습니다.

  CCID 긴 명령·응답 조각을 socket/IFD/컴파일한 native wire 경로에서 처리합니다.
  전송 전용 fixture로 최대 ISO APDU 65544바이트와 긴 응답의 중간·마지막 조각을
  확인했습니다. 이는 PIV가 같은 크기의 데이터를 저장할 수 있다는 뜻이 아닙니다.
  카드 승인을 기다릴 때 native CCID가 시간 연장 응답을 보내고,
  클라이언트 연결 종료가 승인 대기를 취소하여 공유 상태 잠금을 해제합니다.
  macOS kqueue로 아직 읽지 않은 후속 요청 뒤의 연결 종료도 감지합니다.
  시간 연장의 500ms 간격은 소프트웨어 모델이며 실제 키의 타이밍은 미측정입니다.
  bulk-first ABORT가 빠르게 완료되는 경우의 상태 경합을 수정하고
  40회 연속 완료·즉시 SDK 재사용을 확인했습니다.

  PIV 앱의 조립된 평문 데이터 버퍼를 3072바이트로, 객체 값의 합을
  51200바이트로 제한했습니다. 14KiB 저장을 거부하고 교체·삭제·재시작,
  용량 초과 시 롤백, 개인키 저장의 분리와 자체 CA 인증서의 용량 반영을 확인했습니다.
  네 가지 PIN 보호 데이터와 객체 태그·GET/PUT 헤더도 검사합니다.
  PIV 수치는 공식 문서에 기반한 모델입니다. 실제 APDU 헤더/NVM 할당 오버헤드와
  문서의 인증서 3052바이트 경계는 아직 동일하다고 검증하지 않았습니다.
  고정 SDK의 extended APDU 한도는 3062바이트입니다. 더 긴 ISO 명령 조립 검사는
  새 short formatter를 사용하며, 기본 SDK 경로의 한도를 바꾸지 않았습니다.

기존 CCID 취소·파라미터 처리는 유지합니다. 성공 연산은 저장과 취소의 공통 완료
경계를 사용하고, 이미 수행한 인증 실패는 응답 취소 뒤에도 재시도 횟수를 소비합니다.
USB 리셋은 대기 요청을 취소하고 이전 세대 응답을 버립니다.
이 취소·reset 전환은 fresh 상태와 wire 모델 검증입니다. 기본 Linux 실제 USB
등록은 검증했으며, 해당 전환의 실제 버스 및 macOS 검증은 남아 있습니다.

기존 프로토콜과 전송

  실제 GetInfo에서 확인한 버전 순서와 한도를 반영했습니다.
  전체 CTAP 메시지 1536바이트, credential ID 한도 128바이트,
  최소 PIN 길이를 공개할 RP 1개, LargeBlob 조각 1472바이트입니다.
  AAGUID와 firmwareVersion(3)은 독립 소프트웨어 모델의 값입니다.
  기존 기준 키와 새 에뮬레이터의 PIN 설정·저장된 자격 증명 수도 다릅니다.

  IFD Handler 3.0 네이티브 reader 드라이버를 추가했습니다.
  bin/macos-arm64/ifd-ske.bundle의 직접 ABI 호출과 SDK APDU 경로를 검증했습니다.
  이 번들은 시스템 PC/SC에 설치한 상태가 아니며, 자체적으로 USB reader를 만들지 않습니다.
  직접 연결은 같은 사용자의 private Unix 소켓을 사용합니다.

  ske-usbd에 공개 IOUSBHostControllerInterface 전송 소스를 추가했습니다.
  하나의 USB 설정에 OTP 키보드·FIDO HID·CCID 인터페이스를 구성합니다.
  USB 제어 요청, HID feature report, CCID 프레임 분할·조립, 엔드포인트 정지,
  재설정, 키보드 프로토콜·LED·idle 반복·버튼 출력의 wire 모델을 검증했습니다.
  --yubico-usb-ids는 SDK가 검사하는 공개 USB ID/PID와 reader 이름을 맞춥니다.
  7가지 인터페이스 조합을 SDK 판별식과 대조했습니다. 제품 이름에 software를 표시하며,
  새 키·일련번호·별도 AAGUID·자체 증명 인증서를 사용합니다.
  macOS에서 수정본의 실제 OS 장치 등록과 자동 탐색은 아직 검증하지 않았습니다.

실행 — 이 폴더에서

  uv sync
  uv run python emulator.py test
  uv run python emulator.py device

device 모드는 카드/FIDO 상태를 work/device/에 보관하고, 짧은 private 소켓 경로를
출력합니다. 일련번호와 USB 앱 설정을 공유합니다. 사용자 존재 확인이 기본입니다.
자동 시험에서만 --testing을 명시하여 터치를 모사합니다.

개별 실행:

  uv run python emulator.py fido
  uv run python emulator.py card

소스 빌드:

  uv run python emulator.py build
  uv run python emulator.py test --binary-dir work/build

C++23, CMake/Ninja, OpenSSL 3 개발 파일과 macOS SDK가 필요합니다.
동봉 바이너리는 이 맥의 macOS 27.0.1 ARM64 Debug 빌드입니다.
Python 3.12 이상과 uv를 사용하며 의존성은 uv.lock에 고정했습니다.

macOS 네이티브 USB 연결

ske-usbd에는 본인 개발자 팀에서 정식 프로비저닝한
com.apple.developer.usb.host-controller-interface 권한이 필요합니다.
source/packaging/macos/composite.entitlements.plist는 필요한 권한을 기술하는 소스입니다.
이 파일만으로 실행 권한이나 유효한 개발자 서명이 생기지는 않습니다.
사용자가 아직 서명 환경이 없다고 답해 소스·프로토콜 구현을 계속했습니다.

권한과 서명 준비 후, 실행 중인 device의 소켓을 지정합니다.

  uv run python emulator.py usb --card-socket <카드 경로> --fido-socket <FIDO 경로> --yubico-usb-ids

전용 터미널에 hold 500 / hold 3500을 입력하면 짧은/긴 버튼 동작을 요청합니다.
이 실행 모드는 실제 키보드 리포트를 보낼 수 있습니다.
검증 도구는 --wire-test만 실행하며 OS 장치를 만들거나 키를 타이핑하지 않습니다.

별도 IOHID 전송은 com.apple.developer.hid.virtual.device 권한이 필요합니다.
동봉된 prebuilt/swpasskeyd.app은 수정하지 않은 원본 0.2.0 서명 앱입니다.
원본 앱의 브라우저 검증 결과는 수정본을 검증한 결과와 구분합니다.

  OATH: HOTP/TOTP SHA1/256/512, 목록·계산·이름 변경·삭제·접근 코드·초기화.
  OTP: 2개 슬롯 설정·교환·접근 코드·스캔 맵, HID 8바이트 report/CRC,
       HMAC-SHA1/Yubico challenge-response, HOTP/Yubico OTP/정적 비밀번호,
       키보드 수정자·누름/해제·지연, 휴면·슬롯 보호·버튼 hold/release,
       단일 정적 ticket 슬롯의 변경 준비/확정 동작.
  SCP03/SCP11a/b/c: SDK 핸드셰이크, 암호화·MAC·receipt,
                  호스트 인증서 체인·유효기간·CA 제약·허용 목록.
  Security Domain: AES/P-256 키 세트, KCV·인증서·CA SKI·허용 목록·삭제·초기화.
  Management: CCID/OTP/FIDO vendor 0x42/0x43, 일련번호·USB 앱 설정 공유와 잠금.
  저장: AES-256-GCM, 원자적 쓰기·실패 롤백·0600 파일/소켓·실행 잠금.

남은 검증과 차이

Linux guest의 UHID/hidraw 및 실제 복합USB 버스·stock FIDO/OTP·evdev·libccid/pcscd는 검증했습니다.
Firefox 기본 USB WebAuthn, PIN/UV·discoverable·다중 계정 선택, PRF와 자체
attestation 동의·거절과 Chromium 두 알고리즘의 largeBlob은 검증했습니다. 남은 확장·attestation 조건,
다른 브라우저 및 macOS PC/SC/키보드 등록,
Linux dummy_hcd에서 명시된 중단·PM·재연결 범위는 위 보고서로 검증했습니다. 다른 controller/doorbell/완료 순서와 추가 동시 요청·물리 동작은 미검증입니다.
CCID 조각·시간 연장의 실제 키 차등 타이밍, 기준 ATR/T=1 전기 파라미터 비교,
PIV의 정확한 인증서/할당 경계·F9 인증서 파싱 제약·거부 status 차등 비교와
OpenPGP의 정확한 쓰기 status·할당/SCP 오버헤드·내용 허용 범위·aggregate PUT·
증명 키/인증서 보존과 metadata/UIF 초기화의 실제 차등 비교·생성 leaf 확장 형식·
교체 인증서 파싱/거부 규칙·미공지 알고리즘/가져오기 형식 허용 범위·
P-521 padding/SDK 상호 운용·확장 CRT·서명 counter 초기화/포화,
Security Domain 인증서 권한 확장·정확한 키 한도/재시도,
OTP 디바운스·FAST_TRIG·시작 시 serial 입력·LED·두 MAN_UPDATE 슬롯 선택·legacy
동작, OATH malformed 입력 허용 범위/검사 순서·최대 secret/challenge·카운터 포화와
전체 표준/차등 적합성 검사가 남아 있습니다.
CCID 1.1은 CMD_NOT_ABORTED의 숫자 값을 지정하지 않아 모델에서는 CMD_ABORTED를 사용합니다.
미완성 bulk-first ABORT 쌍에는 private 전송의 25초 대기 한도가 있습니다.
같은 카드 서비스의 공유 상태 잠금 때문에 모든 앱 요청의 동시 진행을 보장하지 않습니다.

새 소프트웨어 비상주 FIDO 키의 항목 수 제한은 없습니다. 상주 용량은 100개입니다.
하드웨어 백엔드와 이전 버전 비상주 항목에는 저장된 핸들/행 방식과 전체 10000개
저장 한도가 남아 있습니다. 실제 credential-ID 형식, 카운터 초기값·업데이트·포화와
비상주 credBlob 경계 응답은 미검증입니다. 제조사 비밀키·공장 증명 신뢰·보안칩·
물리 터치 보장은 재현하지 않았습니다. 같은 사용자가 래핑키를 읽을 수 있는 소프트웨어 저장입니다.
기본 스마트카드 PIN·관리키와 SCP03 키는 공개 개발 프로파일 값입니다.
이 프로젝트에는 제조사 신뢰나 공식 FIDO 인증이 없습니다.
