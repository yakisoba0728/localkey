# v55 OpenPGP attestation Le boundary

Published v0.54 `emucard/core.py` SHA-256: `dc16113dac3b2e0c852303f9caf605d4106155932f9bebadc7724cc1179f2154`. Isolated `source.patch` SHA-256: `c6bee2ae5920d1f95d26b6ab7cd8bda391405cddce9a80a2c38167ee358b6c10`. Candidate core SHA-256: `0d2404fb7d003ae2e3d22f82cbdcc1395672a4646f5b6587defd90471696723f`. The patch changes only the OpenPGP `INS FB` branch. Published outputs and shared staging were not edited.

Yubico's [OpenPGP Attestation protocol](https://developers.yubico.com/PGP/Attestation.html) specifies `CLA=80`, `INS=FB`, `P1=01/02/03`, `P2=00`, no command data, `Le=00`, and no response data. Successful execution replaces the corresponding cardholder certificate. Yubico's [OpenPGP 5.2.3 enhancements](https://developers.yubico.com/PGP/YubiKey_5.2.3_Enhancements_to_OpenPGP_3.4.html) describe the fourth attestation certificate occurrence and the AUT→DEC→SIG→ATT ordering; the candidate leaves that model unchanged.

In v0.54, a raw `80 FB 01 00 01` APDU with explicit short `Le=1` returned `9000` and replaced an existing SIG certificate. The resulting state persisted. The candidate checks `Le` before invoking attestation, returning `6700` and retaining the certificate and persisted state. It continues to accept absent Le and zero-encoded short/extended Le for the normal SDK/extended APDU path. The exact 5.7.4 hardware rejection status and tolerance for these encodings remain unmeasured.

`results/before-socket.json` and `before-ifd.json` show the original success and certificate overwrite through a private CCID socket and direct IFD ABI. `results/after-socket.json` and `after-ifd.json` show `6700`, no overwrite, and byte-identical persisted state. Each run also used unmodified YubiKit to generate the SIG key, import/read the original certificate, perform a normal attestation, and independently verify the certificate signature against the emulator's own ATT issuer. No physical key or host PC/SC was opened.

Relevant regressions passed on the candidate: attestation lifecycle 66 checks on socket and 66 on IFD; four-slot/OpenPGP extensions 28 on socket; OpenPGP object/profile checks 119 on socket and 119 on IFD; APDU header checks 21 on socket and 21 on IFD; previous GET NEXT DATA exhaustion and malformed-Lc checks on both transports. These confirm software and saved-reference compatibility only, not perfect physical firmware equivalence.
