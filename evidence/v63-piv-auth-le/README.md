# v63 isolated PIV `GENERAL AUTHENTICATE` Le candidate

Yubico's PIV APDU references specify `Le` as absent for `INS=87` [sign](https://docs.yubico.com/yesdk/users-manual/application-piv/apdu/auth-sign.html), [decrypt](https://docs.yubico.com/yesdk/users-manual/application-piv/apdu/auth-decrypt.html), [key agreement](https://docs.yubico.com/yesdk/users-manual/application-piv/apdu/auth-key-agree.html), and [management-key authentication](https://docs.yubico.com/yesdk/users-manual/application-piv/apdu/auth-mgmt.html). Unmodified YubiKit 5.9.2 emits an APDU with no Le for `PivSession.sign`.

The v62 integration-stage baseline core SHA-256 is `e485006eb471c0f34055b190f40bc5d8b66b57f11924d5b6548b2bfa3da427df`. An added `Le=01` to an otherwise valid ECC P-256 SIGN APDU made this emulator sign, return one byte and `61xx`, and consume the verified authorization of a `PIN_POLICY.ALWAYS` key. The next unmodified YubiKit signature then failed with `6982`. The returned signature could be assembled through GET RESPONSE and verified against the generated public key. Persistent PIV state was semantically unchanged, although the baseline rewrote the encrypted state file.

`source.patch` places a single `a.le is None` guard before the PIV `INS=87` command parses TLVs or uses a key. In the candidate, the malformed APDU returns `6700`, leaves encrypted state bytes unchanged and leaves PIN_ALWAYS authorization available. The following normal YubiKit signature succeeds and verifies. Normal PIN_ALWAYS consumption, management-key/SCP03 operation and persistence after restart remain covered.

The A/B driver `verify_piv_auth_le.py` passed on macOS and Linux ARM64, on both a private CCID Unix socket and direct native IFD Handler: 8/8 route/build runs. The candidate also passed 18 regression runs and 710 enumerated checks: PIV profile 60 checks on each of four platform/route combinations; broad smartcard 97 checks on each of four; PIV storage 31 checks on both platforms; PIV management-header/SCP03 and PIV GENERATE P1 focus on each of four. Results and their individual SHA-256 hashes are in `results/` and `evidence.json`. Direct IFD used v62-stage compiled binaries, macOS SHA-256 `b99e2d71658954664bc5e1e203249aa7085407bf9edecf3f77df493ce556d267` and Linux ARM64 SHA-256 `1412bb9fb2c0b10a63bbbf4885f6a4f6b959d378d40704e760673f487f2fd554`. The Linux guest ran with `--network none`, read-only root, dropped capabilities, no new privileges and no passed-through devices. Neither a physical key nor host USB/HID/PCSC/Keychain was accessed.

`source.patch` SHA-256: `6cf7a1fc0f81f43a480727dd16303d1df8082dff266fb171d0063c1c77a84483`; candidate core SHA-256: `01d693a5ee5e1ab4781a62d6617822b9113d1e66a557dc6d359becc23d384086`. The patch applies cleanly to the recorded v62-stage baseline. Publication of v0.62 and its final core SHA still require rechecking before integration.

The YubiKey 5C Nano firmware 5.7.4 error status for this malformed APDU was not measured. `6700` is the candidate's APDU-length rejection choice based on the documented command shape; the physical key's exact response and other firmware tolerances remain unknown. This evidence supports SDK/protocol fidelity and local state preservation, not complete physical equivalence.
