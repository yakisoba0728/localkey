# v0.49 Linux FunctionFS Full Speed policy

Yubico lists the 5C Nano data-transfer rate as [12 Mbps](https://www.yubico.com/product/yubikey-5c-nano/), the USB Full Speed rate. The previous Linux bridge registered only Full Speed FunctionFS descriptors but left a high-speed-capable ConfigFS controller free to negotiate High Speed. In an owned no-NIC ARM64 dummy_hcd guest, that combination repeatedly produced `no configurations` and `can't read configurations, error -22` before any application could enumerate. The raw failed console is retained under `evidence/v48-protocol-and-transport/linux-highspeed-gap/`.

The minimal default bridge writes `max_speed=full-speed` to its operator-prepared ConfigFS gadget before opening FunctionFS ep0 and binding the controller. This changes only `source/src/usb/linux.cpp`; `default-bridge/applicable-source.patch` can be applied from the package root, while `default-bridge/source.patch` is the exact build-candidate diff referenced by `result.json`. Neither the USB descriptor model nor endpoint addressing is changed.

A positive control set that ConfigFS attribute externally with the previous bridge and passed the native 28/122/8 OTP/HID/PCSC, stock libccid/SDK and valid X.509 scopes. The new bridge combined with the exact v0.49 card source and the v0.48 Linux CTAP daemon passed those same scopes on a high-speed-capable controller. The host reported six Full Speed attachments and zero High Speed attachments, with no kernel panic. Input manifests, bridge build hashes and raw console logs are adjacent. The second full-speed-only controller boot passed the same 28/122/8 scopes and kept all six observed attachments at Full Speed.

These are finite dummy_hcd observations. Production UDCs, external macOS/Windows/Linux USB hosts, physical YubiKey 5C Nano firmware timing and entitled macOS device registration remain unverified. The optional High Speed descriptor experiment is outside the default product patch because the reference product specifies 12 Mbps.
