# v62 OATH cross-client authorization candidate

Yubico's [YKOATH protocol](https://developers.yubico.com/OATH/YKOATH_Protocol.html) says PUT, LIST, CALCULATE, CALCULATE ALL, SET CODE, DELETE, and SEND REMAINING require a successful VALIDATE when an access code is configured. The published v0.61.0 emulator kept only a per-connection `oath_authenticated` boolean. When one private CCID client changed the shared code, a second client retained its earlier authorization. It could insert a credential or read a pending LIST continuation without authenticating to the current code.

`source.patch` changes only `emucard/core.py`. It binds each connection's OATH authorization to the current application salt, access key, and a revision renewed on each successful SET CODE. This also closes a K1→K2→K1 round trip. The guard covers both ordinary OATH commands and pending SEND REMAINING/GET RESPONSE data. An authenticated client that changes its own code remains authorized, as required by the stock YubiKit `set_key` flow.

`verify_oath_auth_binding.py` uses two independent private CCID connections and unmodified YubiKit `OathSession`. It records four stale PUT cases and two stale continuation cases. All four Mac/Linux socket/direct-IFD routes reproduce the published behavior: PUT succeeds with SW `9000`, inserts a credential, and changes decrypted state; A5/C0 returns previous protected LIST bytes. In the candidate, PUT and continuation return `6982`, no credential is inserted, no protected bytes are returned, and ordinary YubiKit reauthentication succeeds. See `results/baseline-*.json`, `results/fixed-*.json`, and machine-checked `validation.json`.

Regression reports in `results/` record 107 OATH and 97 general smart-card checks per route, plus the existing OATH continuation check. Mac tests use a private Unix socket or direct IFD ABI. Linux tests run in an owned container with `--network none --cap-drop ALL` and the same private transports. No physical YubiKey, host PC/SC reader, USB/HID, keyboard, Keychain, or network device was used.

This is a specification-backed emulator defect and software verification. Exact YubiKey 5.7.4 multi-client scheduling and status behavior remain unmeasured on physical hardware.
