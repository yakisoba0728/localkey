# v0.62 isolated PIV GENERATE P1 candidate

Published v0.61.0 `emucard/core.py` is copied byte-for-byte into `baseline/` (SHA-256 `fc663baf17c6a66bffe5e6aae1bdf70d9dd9bf5ba1206c12eca6e9d901b25116`). `source.patch` changes only the PIV `INS 47` branch. It checks P1=00 before replacing a private key and dry-runs cleanly against that baseline. The candidate core SHA-256 is `a76541485a8619bd0ae6d52fb22dafdf181e8d1a98e6b23f67c8a8f60ba1f37a`; the patch SHA-256 is `d90566052685e2a7b7fb03133d2f19fac1d785083990c70c9b8e45ff3cd36303`.

Yubico's [PIV GENERATE ASYMMETRIC KEY PAIR APDU table](https://docs.yubico.com/yesdk/users-manual/application-piv/apdu/generate-pair.html) specifies `CLA=00, INS=47, P1=00`, a slot number in P2, an `AC` key template, and no Le. The document notes that generating into an occupied slot replaces the old key. The unmodified Python YubiKit `PivSession.generate_key` emits P1=00 in the independent test.

On the published emulator, `00 47 01 9A 05 AC 03 80 01 11` and the same command with P1=FF both returned `9000` and replaced an existing ECC P-256 private key in slot 9A. Its public key changed, and the replacement survived a private service restart. The candidate rejects both with `6A86` before generation; the original public key, decrypted PIV key state, and encrypted state file bytes remain unchanged. After restarting the same card, unmodified YubiKit successfully generates a new key with the documented P1=00 form, and that new key persists after another restart.

The same A/B driver ran on macOS and Linux ARM64 through a private CCID Unix socket and a compiled direct IFD ABI: two malformed P1 values on each of four platform/route combinations. The candidate also passed 60 PIV profile checks per socket/IFD route, 31 PIV storage checks per socket route, and 97 broad smartcard checks per socket/IFD route, for 690 regression checks across both platforms. Raw JSON and hashes are in `results/summary.json`. Linux ran in a `--network none`, read-only ARM64 container with private `/tmp`, no added devices, and no privileges.

This is a documented APDU-shape correction with independent SDK compatibility evidence. `6A86` is the emulator's error choice; the physical YubiKey 5C Nano firmware 5.7.4's malformed-P1 tolerance/status was not measured. No physical key, host USB/HID/PCSC/Keychain, published output, or shared staging was accessed for writes.
