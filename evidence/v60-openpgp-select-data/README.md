# v0.60 isolated OpenPGP SELECT DATA Le candidate

Published v0.59.0 `emucard/core.py` baseline SHA-256: `9ec868235c409c57d3699a32ba14e87c86d2b81c4c134391b923df0ff0fd3760`. The isolated patch changes only the OpenPGP `INS A5` SELECT DATA branch. It dry-runs cleanly against the copied baseline, produces candidate core SHA-256 `eb91ac52aa5f9f17a62f7dbe7875496bc33936a3e1213cda9ed9df894cb1a37a`, and has SHA-256 `67787f0e59f9fe85925d7644c32c4c9979067e0d85487df1a3e3270b2a49636a`.

The primary [OpenPGP Smart Card Application 3.4.1 specification, §7.2.5 SELECT DATA](https://gnupg.org/ftp/specs/OpenPGP-smart-card-application-3.4.1.pdf#page=57) defines Le=00. The published emulator ignored Le and accepted `00 A5 02 04 06 60 04 5C 02 7F 21 01`. On a card with distinct AUT and SIG certificates, that malformed Le=1 command returned `9000` and moved the current certificate from AUT to SIG. The candidate rejects Le=1 with `6700` before changing the volatile selection; a subsequent GET DATA still returns AUT.

The candidate accepts Le=00 as written in the specification and the Le-absent form emitted by the unmodified Python YubiKit `OpenPgpSession.get_certificate` and `put_certificate`. The same test also issues the malformed command through YubiKit's unmodified `SmartCardProtocol.send_apdu`: it succeeds on the baseline, raises `6700` on the candidate, and preserves the expected certificate selection. AUT/SIG X.509 certificates are created independently and read back through the SDK before and after a private service restart. Persistent decrypted card state remains equal across the malformed command on both versions; the regression is the externally visible volatile selection pointer.

`candidate/tools/verify_pgp_select_data_le.py` and the identical baseline driver ran on macOS and Linux ARM64, each through a private CCID socket and a compiled direct IFD ABI. All four A/B paths passed. The candidate also passed, per path, 97 smartcard checks, 119 OpenPGP object checks, and 21 APDU-header checks. OpenPGP extension checks passed 28/28 on macOS and Linux sockets. See `results/summary.json` and individual JSON reports.

Linux ran in a no-network ARM64 container with read-only candidate source, a private `/tmp`, and no host device passthrough; direct IFD connected only to the private socket. The test did not exercise Linux kernel USB or host PCSC. Published outputs were not modified, and no physical key or host USB/PCSC/Keychain was accessed. The exact malformed-Le status or tolerance of physical YubiKey 5C Nano firmware 5.7.4 is unmeasured; this is a specification-backed software correction, not proof of complete firmware equivalence.
