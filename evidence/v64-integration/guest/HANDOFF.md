# v64 integrated no-NIC USB guest handoff

The integrated v64 stage was tested in an ARM64 Linux QEMU guest using `dummy_hcd` and FunctionFS. The guest had no NIC, no physical or host USB passthrough, and no access to host HID/PCSC/Keychain. The frozen v56 native USB suite supplied the guest userspace and verification programs; `prepare_stage.py` overlaid the v64 stage's 15 `emucard/*.py` files and Linux `ske-usbd`, `swpasskeyd`, and `ske-otpd` binaries. `inputs.json` records every source and binary SHA-256, the base image, the 6.8.0 guest kernel and the resulting guest-image SHA-256.

The same guest image SHA-256 `14a3b8a0c826401b63d93efba8bf0ec765e51ab2d0b001ac2100382cb82fd147` was booted twice. The first execution had QEMU runner exit 0, but only the first ten verification exit markers were 0; `SKE_SEVEN_PROFILES_EXIT=1` and `SKE_V64_STAGE_COMBINED_EXIT=1`. Its console SHA-256 is `e553cfdbcf519aba11a84fd257d17a349ec41d695b9a6a8ff050f0169c5ef2f9`, preserved at `attempt1/console.log` with `attempt1/run.json`. Around guest time 232 s, the kernel warned in `__queue_work` from the `usb_f_fs`/`dummy_hcd` asynchronous completion path; `ske-usbd` then logged a FunctionFS asynchronous endpoint transfer failure (`Operation now in progress`), followed by HID `EIO` and fixture `BrokenPipeError`. The initial cause of this guest-kernel/FunctionFS event is not proven. It did not occur in the v63 successful console.

The second execution used the identical guest image and kernel and had all 12 exit markers equal to 0, with no kernel warning, panic or traceback. Its console SHA-256 is `ad2a2fd951ebcd0ece20abbbc8c5e7df5581086190905fbfd4f08f5672dfeb18`. `seal_stage.py` verified both attempts' console and image hashes, the first failure signatures, the second run's ordered 12 zero markers, and QEMU runner exit 0. The saved `stage-combined/result.json` has `passed: true` and `retry_success_after_first_failure: true`; it deliberately includes `first_attempt` as failed. No source or stage binary was changed between boots. The integrated gate passed on retry, while guest-kernel/FunctionFS timing stability remains unresolved and should be stress-tested before claiming repeatable success.

The stage's Linux `swpasskeyd` SHA-256 was `47f383d48f3d381431c185b816a67131191348cadb3da2b9d16a843df2befaac`; `ske-usbd` was `73e6ed737d3302c726bdb8f721ac2cd940f679a6355077d46e1ac7dc9611c687`; `ske-otpd` was `6e385471243f6f1f75844012cfaa9b052da3b98bf7acb4eaaa16db3f072d55a0`. The v63 successful guest used the same frozen base image SHA `3ab43741f396c63bb3b2fe62a79afb0598b4f4f59b0be57d65ac47acb7b90fb1`, kernel SHA `6001f54164a5201cd5a80e0a09bb05c43fa6e910a0abfe0f5a4e8d7d781cc737`, and USB backend header source SHA `c57ecc0c180eddb5af727f11e13e0ac4fa2c3ef7f0492ce0f291b6e33604912b`. The v64 overlay changed card `core.py` and `domain.py` and rebuilt all three Linux binaries.
