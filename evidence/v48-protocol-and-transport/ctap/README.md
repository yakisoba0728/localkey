# v0.48 isolated CTAP 2.1 minPinLengthRPIDs candidate

The published v0.47 C++ authenticator cleared its existing minimum-PIN RP-ID allowlist when an AuthenticatorConfig `setMinPINLength` request supplied an empty `minPinLengthRPIDs` array. [CTAP 2.1 §6.11.4](https://fidoalliance.org/specs/fido-v2.1-ps-20210615/fido-client-to-authenticator-protocol-v2.1-ps-20210615.html#sctn-setMinPINLength) updates the list only when that parameter is present and contains at least one string. The candidate retains the previous list while still updating a supplied minimum PIN length.

`source.patch` adds one production guard and a Catch2 regression test. The test first stores `example.com` with minimum length 4, then sends an empty list with length 5; the expected final state is length 5 and the retained `example.com` list. The published baseline failed the final assertion (4/5 assertions passed). The candidate passed 5/5. The unmodified python-fido2 SDK over private CTAPHID also observed no `minPinLength` extension in the published baseline after an empty list and the retained value 8 in the candidate. A full isolated host C++ run passed 121 cases and 11,625 assertions. Logs, exact source and binary hashes, and the spec URL are adjacent to this file in `baseline-test.log`, `candidate-focused.log`, `candidate-full.log`, and `validation.json`.

The build uses an isolated CMake/Ninja tool directory and the bundled Catch2 source. It disables TPM and platform integration tests, matching the package's existing software-engine configuration. No physical key, system USB/HID device, Keychain, or Secure Enclave was accessed. The behavior of YubiKey 5C Nano firmware 5.7.4 for this empty-list request has not been measured; this change aligns the software model with the published CTAP standard.
