# Isolated OpenPGP GET DATA command-chain guard

Base: published v0.51 `outputs/security-key-emulator/emucard/core.py`, SHA-256 `f72d3d0c3fd01516d085077c8926871c21f388d60f230e6517cf827d63cc9103`. Candidate core SHA-256: `00e5a6c768d2ab8b8d0b3dec32a722ff53f31ec7a239a7148d1a480c812b49d6`. The only Python source change in `candidate/emucard` is `core.py`. `source.patch` SHA-256: `edb9fd50b0746dad4f3a3396182f00e76000b3cc339847d6c64ad08fd270e889`; it passes `patch --dry-run -p1` against the copied baseline.

The [OpenPGP Smart Card Application 3.4.1, §7.2.6](https://www.gnupg.org/ftp/specs/OpenPGP-smart-card-application-3.4.1.pdf) defines GET DATA CLA `00/0C`. Section 7.4 defines CLA `10` as an intermediate command-chain fragment, and §7.7 requires the card to wait for a matching final fragment after accepting one. Published v0.51 accepted `10 CA 00 6E 01 58` with `9000` as a GET DATA chain start, although GET DATA has no chained CLA. A following ordinary SDK read of a different data object then failed with `6883` because it was mistaken for the final fragment. The candidate checks the OpenPGP GET DATA class before recording a chain and returns `6E00`; the next SDK read succeeds immediately. The exact physical firmware rejection status for this malformed command is unmeasured.

`candidate/tools/verify_openpgp_getdata_chain.py` provides independent before/after evidence through both a private CCID socket and direct IFD ABI in `results/before-{socket,ifd}.json` and `results/after-{socket,ifd}.json`. On each fresh software card, unmodified YubiKit first completes a GET DATA response chain and a 300-byte PUT DATA command chain. The invalid GET DATA prefix then changes from `9000` to `6e00`; the first subsequent SDK read changes from `6883` to `9000`. Data objects remain unchanged.

Existing candidate regressions pass on both transports: the v0.51 GET RESPONSE interruption test, previous GET RESPONSE envelope/SDK test, OpenPGP APDU headers (21 checks), GENERATE Le (44), and OpenPGP objects/SDK crypto and state (119). JSON reports are in `results/`. This candidate does not implement secure-messaging CLA `0C`; actual YubiKey 5C Nano firmware 5.7.4 handling and timing were not measured. Published outputs, host PC/SC/USB/HID, and the physical key were untouched.
