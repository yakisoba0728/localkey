# v0.50 isolated CTAP 2.1 enterpriseAttestation type candidate

The published v0.49 C++ authenticator parses `authenticatorMakeCredential` parameter `0x0A` as CBOR boolean. [CTAP 2.1 §6.1](https://fidoalliance.org/specs/fido-v2.1-ps-20210615/fido-client-to-authenticator-protocol-v2.1-ps-20210615.html#makecred-enterpriseattestation) defines it as an unsigned integer. This software authenticator does not advertise enterprise attestation capability, so a well-typed request should reach the capability check and return the model's `CTAP1_ERR_INVALID_PARAMETER` (`0x02`) before creating a credential. The previous parser instead returned CBOR unexpected type (`0x11`) for integer values and accepted a boolean far enough to return `0x02`.

`source.patch` changes the parser to read and retain an unsigned integer, including zero as a present parameter. The existing capability check remains and rejects it. The test fixture now encodes the standard integer type. In an isolated baseline build, the focused test failed on status `17` versus `2` after 5/6 assertions; the candidate passed 14/14. The full host C++ test suite passed 121 cases and 11,627 assertions. Unmodified python-fido2 over a private Unix CTAPHID socket independently sent integer values 0, 1, 2, 3 and a boolean: the published baseline returned `17` for the integers and `2` for the boolean; the candidate returned `2` for integers and `17` for the boolean. `remaining_disc_creds` stayed unchanged for every rejected request.

The exact malformed-command status precedence of physical YubiKey 5C Nano firmware 5.7.4 has not been measured. This change aligns the model with the published CBOR field type while preserving its documented lack of enterprise attestation support. No physical key, host USB/HID device, Keychain, or Secure Enclave was accessed. Logs, raw SDK reports, source and binary hashes are adjacent to this file.
