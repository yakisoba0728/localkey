# Isolated OpenPGP command-chain / GET RESPONSE candidate

Base: `work/security-key-emulator-v50-staging/security-key-emulator/emucard/core.py` (SHA-256 `f0a52853781beb1656766abd1a2b5b85e589ced07c7383eb48003fdd57ae52f5`). Only the copied `candidate/emucard/core.py` differs from that base. Candidate core SHA-256: `6258ca138f8d08475e05ad80ae974dc2c9f8b9b44138af8c6ccf4f43b8543512`. The minimal `source.patch` SHA-256 is `eeb2f7288c58abbe8d7d1a188d3cd49e90d8e62e93856d57c4e6311779911b28`; `patch --dry-run -p1` succeeds against the isolated baseline.

The [OpenPGP Smart Card Application 3.4.1, section 7.7](https://www.gnupg.org/ftp/specs/OpenPGP-smart-card-application-3.4.1.pdf) says that after a chained command fragment, the card waits for another fragment with the same INS/P1/P2 until the final fragment. Section 7.9 lists `6883` for “Last command of the chain expected.” The v50 staging implementation routes GET RESPONSE before its generic chain-header check, so `00 C0 00 00` sent after `10 DA 00 5B 01 41` returns `9000`, although the card is still waiting for the rest of PUT DATA. A subsequent ordinary SDK GET DATA then fails with `6883` and aborts the chain. The candidate checks for an unfinished OpenPGP chain before GET RESPONSE, returning `6883` at the interrupting command. Its existing error handler clears the abandoned chain, and the next SDK GET DATA succeeds. This changes only the OpenPGP GET RESPONSE branch.

`candidate/tools/verify_openpgp_chain_interruption.py` reproduces the before/after behavior through both a private CCID socket and the emulator's direct IFD ABI. Each run first uses **unmodified YubiKit** with `force_short=True` to write and read a 300-byte OpenPGP certificate through valid command chaining, then tests the invalid interleaving. Reports: `results/before-{socket,ifd}.json` show GET RESPONSE `9000` and the first following SDK read `6883`; `results/after-{socket,ifd}.json` show GET RESPONSE `6883` and the first following SDK read `9000`. In both versions the preexisting Name object remains unchanged and later SDK writes/reads work.

Additional candidate regressions passed on each transport: the prior OpenPGP GET RESPONSE envelope/SDK verifier, APDU headers (21 checks), GENERATE Le (44), and OpenPGP objects/SDK crypto and state (119). Reports are in `results/`. The exact rejection behavior of a physical YubiKey 5C Nano firmware 5.7.4, USB timing, and secure messaging command chaining have not been measured. No physical key, host PC/SC/USB/HID, published outputs, or v50 staging source were modified or accessed as devices.
