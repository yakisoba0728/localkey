# v64 YubiHSM Auth symmetric challenge touch candidate

Yubico's [credential description](https://docs.yubico.com/yesdk/users-manual/application-yubihsm-auth/objects/credential.html) ties the optional touch requirement to using a credential **to calculate session keys**. Its [session API](https://docs.yubico.com/yesdk/yubikey-api/Yubico.YubiKey.YubiHsmAuth.YubiHsmAuthSession.html) describes `CreateHostChallenge` for a symmetric credential as generating a random eight-byte host challenge, and describes touch during `GetAes128SessionKeys`. The [YubiKit source](https://developers.yubico.com/yubikey-manager/API_Documentation/_modules/yubikit/hsmauth.html) has separate GET CHALLENGE and CALCULATE calls.

The published v0.62.0 model requires touch for both symmetric GET CHALLENGE and CALCULATE. `source.patch` changes only `emucard/core.py`: symmetric GET CHALLENGE returns a random challenge without touch, while CALCULATE and the existing asymmetric behavior retain their touch checks. It does not change credential storage or retry logic.

`verify_hsmauth_challenge_touch.py` uses the unmodified YubiKit `HsmAuthSession` over a fresh private CCID socket or direct IFD ABI. With no touch approval, the published model returns `6985` from GET CHALLENGE for a touch-required symmetric credential; the candidate returns `9000` and eight bytes. CALCULATE remains `6985` without touch in both models. With software touch approval, both operations succeed and the SDK receives three 16-byte session keys. A credential without a touch policy works normally in both models. All four Mac/Linux socket/IFD A/B routes pass. The existing 97-check smart-card regression passes on each candidate route. Exact report names and SHA-256 hashes are in `validation.json`.

Mac tests use isolated Unix sockets or direct IFD calls. Linux tests run with `--network none --cap-drop ALL`. No physical key, host PC/SC, USB/HID, keyboard, Keychain, or network device was used. The physical 5.7.4 timing and status for this boundary have not been measured, so the candidate is a documented software-model alignment rather than a firmware differential claim.
