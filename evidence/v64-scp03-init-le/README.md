# v64 isolated SCP03 INITIALIZE UPDATE Le candidate

The [GlobalPlatform SCP03 specification, section 7.1.1, Table 7-2](https://globalplatform.org/wp-content/uploads/2019/12/GPC_2.3_D_SCP03_v1.1.2.6.pdf) specifies `INITIALIZE UPDATE` as `INS=50`, `P2=00`, eight host-challenge bytes in S8 mode, and `Le=00`. The unmodified YubiKit 5.9.2 `ScpState.scp03_init` calls `send_apdu` with no explicit Le; its formatter emits no Le for this data-bearing APDU. The candidate accepts SDK's absent Le and explicit maximum Le (`00` short or `0000` extended), while rejecting other limits.

The v0.62.0 baseline dispatches `80 50 FF 00 08 <8-byte challenge> 01` to `domain.handshake()` without checking Le. It resets the session, reserves an SCP03 authentication attempt, returns the first response byte plus `61xx`, and commits retry count 64→63. The remainder obtained by GET RESPONSE yields a 29-byte INITIALIZE UPDATE response whose card cryptogram independently verifies using AES-CMAC. This is a real use of the key set on an APDU whose response limit contradicts the documented format.

`source.patch` adds one guard after the existing P2/Lc check and before `reset_for_channel()` and `attempt()`. The candidate returns `6700`, preserves the domain state and exact encrypted state-file bytes, and keeps retry count at 64. It still accepts the GlobalPlatform short `Le=00`; an unmodified YubiKit handshake, encrypted `GET DATA`/CPLC read, retry restoration, and restart succeed.

The A/B driver `verify_scp03_init_le.py` passed on macOS and Linux ARM64 using both a private CCID Unix socket and direct native IFD Handler: 8/8 route/build runs. The candidate passed 12 additional regression runs totaling 4,004 checks: Security Domain profile 71×4, SCP03 version/SDK/cryptogram 833×4, and broad smartcard 97×4. Individual results and SHA-256 hashes are in `results/` and `evidence.json`. The Linux guest used `--network none`, read-only root, dropped capabilities, no new privileges and no passed-through devices. No physical key or host USB/HID/PCSC/Keychain was accessed.

The patch is against the published v0.62.0 `emucard/domain.py` SHA-256 `87a192dd4f76d6d1562abd94d8cef4ea0bd932ddb4e35991c61baffc4c0ea6a1`. Patch SHA-256: `8ed1102893412b93a531957fc8c9bfd4a2118010f81c361279614e913f3c5247`. Candidate module SHA-256: `8e867c2c00eddc776a68c0d1fa5adc0349a27b378010486e228213516f9bc4c4`. Dry-run application to published v0.62.0 succeeds. v63 changes only `emucard/core.py`; its candidate `domain.py` hash equals this baseline, so the patches are source-disjoint.

Exact YubiKey 5C Nano firmware 5.7.4 response to malformed Le, its authentication retry semantics, and extended-Le tolerance were not measured. The selected `6700` is this emulator's APDU-length error policy. The test proves a local protocol/state boundary and SDK compatibility, not physical equivalence.
