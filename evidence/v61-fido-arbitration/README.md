# CTAPHID cross-channel arbitration candidate

The [FIDO CTAP 2.1 specification](https://fidoalliance.org/specs/fido-v2.1-ps-20210615/fido-client-to-authenticator-protocol-v2.1-ps-20210615.html), §11.2.5.1, says that a transaction occupies the device from its first request packet until the last response packet. A different channel's request during that interval immediately receives a busy error. §11.2.9.1.3 describes broadcast INIT as a channel allocation request and gives no arbitration exception; §11.2.9.1.5 requires a non-active CID's CANCEL to be ignored.

Published v0.60 handled another allocated CID's CBOR/MSG as busy, but answered that CID's PING, WINK and INIT, and also answered broadcast INIT while another transaction was assembling or in flight. Broadcast allocation could also reap one of the four tracked CIDs during an active operation. `source.patch` gates these requests before the frame assembler. Same-CID INIT resynchronization and active-CID CANCEL remain available. `test.patch` updates the prior PING/broadcast expectations and checks the busy and idle boundaries.

`validation.json` seals the patch, source, binary, input and raw-log hashes. The Linux baseline-focused tests failed in three expected arbitration cases; both patched Mac and Linux builds passed 136 test cases and 13,687 assertions. Private Unix-socket A/B on Mac and Linux delayed a CBOR operation in a fake card RPC. During the delay, baseline PING/WINK/allocated INIT/broadcast INIT all succeeded; the patch returned CTAPHID_ERROR `0x06` for all four. The active CBOR response and subsequent idle PING succeeded in both modes.

An owned no-NIC ARM64 dummy_hcd/FunctionFS guest confirmed the PING and broadcast INIT behavior through USB endpoints 0x04/0x84. Both guest runs completed with exit code 0 and no observed kernel panic. The guest used a frozen v58 card and bridge, with only the public v0.60 or patched v0.61 FIDO daemon overlaid. The physical YubiKey firmware and production USB device controllers were not measured.
