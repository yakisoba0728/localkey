# OATH catalog status (lk-oath)

One line per bullet of the `## OATH` section of `reference/BEHAVIOR_CATALOG.md`.
Test names refer to `crates/lk-oath`: `tests/protocol.rs`, `tests/vectors.rs`,
`tests/fuzz.rs`, and the unit tests in `src/` (`tests::`, `state::tests::`,
`credential::tests::`, `request::tests::`).

Counting convention: each bullet has exactly one label, the first word after the colon.

- `tested`: the named tests pass and exercise everything in the bullet that a single
  `CardApplet` can show. Notes in parentheses record model-policy choices made where
  the catalog and YKOATH leave a status or detail open. They do not change the label.
- `intentional difference`: the engine deliberately behaves or verifies differently
  from what the bullet (or the public YKOATH wording it rests on) says. The reason
  comes first, then the tests that cover what does apply.
- `deferred`: something the bullet needs is missing.

Totals: 17 tested, 3 intentional differences, 0 deferred.

## OATH

- RFC4226 HOTP: tested: `rfc4226_appendix_d_truncated`, `rfc4226_appendix_d_full_hmac`, `rfc4226_hotp_without_challenge_field`, `hotp_counter_is_persisted_before_the_code`, `credential::tests::dynamic_truncate_rfc4226_appendix_d_count0`, `credential::tests::dynamic_truncate_rfc4226_section_5_4_example`, `credential::tests::dynamic_truncate_largest_offset`
- RFC6238 TOTP: tested: `rfc6238_appendix_b_all_18_vectors`, `rfc6238_full_response_is_independent_hmac`, `rfc6238_through_calculate_all`
- SHA1/256/512 implementation: tested: `rfc6238_appendix_b_all_18_vectors`, `hotp_sha256_sha512_match_independent_hmac`, `long_keys_are_shortened_per_rfc2104`, `credential::tests::shortening_preserves_the_mac`, `sha256_access_key`
- list/calculate/calculate-all/rename/delete: tested: `list_calculate_rename_delete_round_trip`, `calculate_all_full_truncated_and_placeholders`, `calculate_all_mixed_types_touch_and_only_increasing`, `rename_rules`, `name_length_boundaries`, `digits_6_7_8_select_the_code_length`, `missing_credentials_are_6984`
- access key mutual challenge-response: tested: `access_key_flow_with_pbkdf2`, `validate_boundaries`, `sha256_access_key`, `changing_the_access_key`, `access_key_guards_every_credential_command`, `authorization_is_per_selection`, `failed_validate_drops_pending_continuation` (a wrong VALIDATE response is `6A80`. YKOATH §VALIDATE lists only "auth not enabled" `6984` and "wrong syntax" `6A80`, the catalog fixes no status for a wrong proof, and public YKOATH clients recognise a wrong password by `6A80`)
- only-increasing property: intentional difference: a challenge equal to the last one is accepted, while YKOATH §PUT says "always higher". Clients recalculate within one time step (CALCULATE ALL on every refresh), so a strict rule would lock them out until the next step. A lower challenge is `6982`, the highest challenge is persisted, and CALCULATE ALL applies the same rule except to touch placeholders. Covered by `only_increasing_property_is_enforced_and_durable`, `calculate_all_mixed_types_touch_and_only_increasing`, `storage_failures_keep_the_previous_state`, `credential::tests::challenge_comparison_is_numeric`
- reset: tested: `reset_while_locked_rotates_salt`, `storage_failures_keep_the_previous_state`, `header_and_body_validation` (P1 `DE` P2 `AD` only)
- four-byte HOTP-only IMF, singleton property and required/allowed TLV syntax: tested: `put_rejects_malformed_data_before_writing`, `imf_sets_initial_counter_and_is_durable`, `request::tests::property_has_no_length_byte`, `request::tests::malformed_fields_are_6a80`, `request::tests::pick_rejects_unknown_and_duplicate_tags` (property only in the raw YKOATH form `78 xx`)
- command P1/P2/body validation and documented missing-object/auth-not-enabled responses: tested: `header_and_body_validation`, `missing_credentials_are_6984`, `validate_boundaries` (VALIDATE without an access key is `6984`), `access_key_guards_every_credential_command`, `tests::class_byte_rules` (CLA: secure-messaging bits `6882`, logical channel `6881`, other classes `6E00`, as in the device's PIV applet)
- eight-byte SET CODE challenge, variable VALIDATE challenge and SHA1 proof length; incorrect SET CODE proof returns 6984: tested: `set_code_boundaries`, `validate_boundaries`, `sha256_access_key` (VALIDATE host challenge 1..=64 bytes; the 64-byte maximum is model policy because the reference maximum is unmeasured)
- all 18 published RFC6238 SHA1/SHA256/SHA512 vectors and independent HOTP/full/truncated HMAC: tested: `rfc6238_appendix_b_all_18_vectors`, `rfc6238_full_response_is_independent_hmac`, `rfc4226_appendix_d_full_hmac`, `rfc4226_appendix_d_truncated`, `hotp_sha256_sha512_match_independent_hmac`, `rfc6238_through_calculate_all`
- full/truncated CALCULATE ALL and HOTP/touch placeholders without HOTP counter consumption: tested: `calculate_all_full_truncated_and_placeholders`, `calculate_all_mixed_types_touch_and_only_increasing`, `digits_6_7_8_select_the_code_length` (YKOATH gives both `77` for HOTP and `7C` for touch; an HOTP credential with touch is reported as `77`, because clients infer the type from `77`)
- durable IMF/only-increasing state, mutual SDK access-code validation and independent PBKDF2 derivation: tested: `imf_sets_initial_counter_and_is_durable`, `only_increasing_property_is_enforced_and_durable`, `calculate_all_mixed_types_touch_and_only_increasing`, `access_key_flow_with_pbkdf2`, `pbkdf2_helper_matches_rfc6070`, `restart_and_unreadable_state` (the "SDK" side is the client written in the tests: PBKDF2-HMAC-SHA1, 1000 iterations, SELECT salt, 16 bytes. No external SDK runs at engine level, `docs/DESIGN.md` §12-3)
- published 64-credential capacity; overflow, overwrite/rename at full capacity, release/restart: tested: `capacity_is_64_credentials`
- locked app reset rotates OATH salt while retaining PIV own F9 issuer: tested: `reset_while_locked_rotates_salt` (RESET without VALIDATE rotates the salt and writes only `Record::Oath`, and a PIV record in the host is left untouched. Checking the real PIV F9 issuer object across applets is an lk-device integration check)
- socket and direct IFD SDK fixtures; no physical differential or OS reader validation: intentional difference: the engine has no transports or OS readers (`docs/DESIGN.md` §4, §13). Applet behaviour is tested through `CardApplet` with `lk_testkit::TestHost`, and those fixtures belong to the program phase
- 64-bit HOTP terminal counter rejects the exhausted next-counter sentinel without crashing a private socket; physical status unmeasured: tested: `tests::hotp_terminal_counter_is_refused` (counter `u64::MAX - 1` is the last usable one. The sentinel `u64::MAX` is refused with `6985` (model policy) and nothing is written. CALCULATE ALL still shows the `77` placeholder)
- PUT credential secret minimum 14 wire bytes; unpadded 13-byte APDU rejected before persistent write and SDK padded one-byte source verified: tested: `put_secret_minimum_is_14_wire_bytes`
- SEND REMAINING rejects nonzero CLA before consuming a pending response. Mac/Linux private CCID socket/direct IFD A/B and unmodified YubiKit 504-byte list continuation pass; physical rejection status remains unmeasured.: tested: `send_remaining_rejects_bad_cla_without_consuming` (every nonzero CLA leaves the continuation intact, including secure-messaging bits, which the device's secure channel clears on commands it unwraps, and the chaining bit. Statuses `6E00`/`6882`/`6881` are model policy), `send_remaining_serves_long_list`, `le_sets_the_piece_size`, `select_response_continues_while_locked`, `send_remaining_in_the_middle_of_a_chain`, `tests::class_byte_rules`
- Per-client OATH authorization is bound to current salt, access key and rotation revision; stale PUT and pending LIST continuation reject after another client changes the code. Mac/Linux private socket/direct IFD and unmodified YubiKit A/B pass. Physical concurrent-session behavior remains unmeasured.: intentional difference: one `Oath` instance serves one card session, and the applet gets no client identity (`lk_core::Host` has none), so it cannot tell clients apart; neither can a card. What applies is the binding of authorization and pending continuations to a revision that SET CODE and RESET bump. `tests::stale_authorization_and_continuation_are_refused` and `tests::stale_authorization_refuses_a_pending_touch` simulate the other client's rotation. Also covered by `changing_the_access_key`, `authorization_is_per_selection`, `failed_validate_drops_pending_continuation`, `reset_while_locked_rotates_salt`
