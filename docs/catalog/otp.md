## Other model decisions (no catalog bullet)

- Factory state has both slots empty (a real key ships with a Yubico-cloud slot 1 credential, which this engine cannot reproduce).
- Fast trigger applies when slot 1 is touch-triggered and slot 2 is not configured.
- A dormant slot counts as configured (`CONFIGx_VALID`) but not touch-triggered; it types nothing and refuses challenge-response.
- NDEF slot commands (`0x08`/`0x09`) are rejected: the 5C Nano has no NFC interface.
- The programming sequence never wraps back to 0 except when a slot write leaves no slot configured. Advances caused by Management writes (`0x11`, `0x15`) are kept in memory and persisted with the next OTP record write.
- A pending challenge-response is bound to the configuration it was addressed to; if the slot changes before the touch, no response is produced (`pending_challenge_is_bound_to_its_configuration`).
- While a challenge-response (HID or CCID) waits for a touch, the touch belongs to it: `Otp::button`, `touch_down` and `touch_up` type nothing and consume no counter. The wait ends with the touch resolution, a reset write, a new frame, deselect/SELECT, card power-off (CCID), USB reset or power cycle, or at its deadline (`button_during_pending_hid_challenge_types_nothing`, `ended_waits_free_the_button`).
- The legacy mode write (`0x11`) advances the programming sequence unless it is 0, matching yubikit `set_mode`, which tolerates an unchanged sequence only on an "empty" key (sequence 0). A sequence can be nonzero with no slot configured after a `0x12` or `0x15` write (`legacy_mode_write_follows_the_yubikit_programming_sequence_rule`).
- UPDATE applies only the `ykdef.h` update masks (ticket TAB/DELAY/CR bits, configuration pacing bits, all extended bits) and the new access code; other flag bits and the fixed/uid/key fields of the UPDATE payload are ignored rather than rejected, so an UPDATE can never change a slot's mode, secrets or `PROTECT_CFG2` (`update_cannot_change_mode_protection_or_secrets`).
- Access codes: a slot without an access code accepts writes whatever code is supplied; SWAP needs the code of every protected slot at bytes 52..58, so two slots protected by different codes cannot be swapped (`access_code_mismatch_changes_nothing`, `swap_honours_access_codes`).
- The frame CRC is the plain (not complemented) CRC-16 of the 64-byte payload, as ykpers `yk_write_to_key` writes it; responses carry the complemented CRC (`frame_crc_is_the_plain_crc_of_the_payload`, `response_chunks_carry_sequence_and_wrap_to_zero`).
