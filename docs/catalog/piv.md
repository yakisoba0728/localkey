## Model policies (physical 5.7.4 status unmeasured)

Changed by the first independent review (specification text overrides the earlier choice):

- A SELECT of the PIV AID while PIV is selected keeps PIN verification and management key authentication (SP 800-73-4 Part 2 §3.1.1: "the setting of all security status indicators in the PIV Card Application shall be unchanged"); it drops only the per-command state (challenge, pending touch, chain, unread response, PIN-always authorization). Deselection and every reset kind still clear the security status. A SELECT routed to the applet with another AID answers 6A82, with P1 other than 04 6A86, and changes nothing. lk-device must call `deselect()` only when another application is selected.
- PIN policy "always": the authorization armed by a successful VERIFY is cleared by any later command except a VERIFY status query (no data), GET RESPONSE, intermediate chain parts of the operation, and a GENERAL AUTHENTICATE rejected before its PIN check (SP 800-73-4 Part 1 §3.2.1: verified "every time immediately before"). This replaces the stage 2 rule that other commands did not disarm it. CHANGE REFERENCE DATA verifies the PIN but does not arm PIN-always.
- CHANGE REFERENCE DATA of the PIN sets the PIN verified on success (§3.2.2); RESET RETRY COUNTER clears it on a wrong PUK and leaves it unchanged on success (§3.2.3).
- PIN data presented to VERIFY, or as the current value of CHANGE REFERENCE DATA, that is not 8 bytes is 6A80 and consumes no retry (§3.2.1.1, §3.2.2). Any 8 bytes are compared, with a retry spent first (changed by the second review; see below). A new PIN or PUK must be 6-8 non-FF bytes padded with FF (§2.4.3; 6A80). PINs may contain any byte other than FF (Yubico relaxes the §2.4.3 digits-only rule).
- Unsupported key references in VERIFY, CHANGE REFERENCE DATA and RESET RETRY COUNTER answer 6A88 (§3.2.1-§3.2.3), not 6A86.
- Mutual authentication step 2 accepts the trailing `82 00` of Table 19.
- Short APDUs are answered with at most Ne bytes (Le `00` or absent: 256), the rest with 61xx and GET RESPONSE (ISO/IEC 7816-4 §5.1; Appendix A.4.1 command 3). Extended APDUs already worked this way.
- GENERATE accepts the Table 11 parameter `81` for RSA when it is the exponent 65537; any other value, or `81` with a non-RSA algorithm, is 6A80.
- A touch fills the cached-touch window only when the touched operation succeeds.
- The own F9 certificate is stored only if it fits a PUT DATA (3072 bytes) and the budget; a larger one would make the record unreadable on load.

Changed or added by the second review (host request shapes; sources in `tests/interop.rs`):

- The 63CX branch of SP 800-73-4 Part 2 §3.2.1.1 / §3.2.2: eight bytes of PIN data outside the §2.4.3 format (for example eight `FF` bytes) are compared like any wrong PIN, instead of 6A80. python yubikit's `PivSession.reset()` (`ykman piv reset`) blocks the PIN with `verify_pin("")`, eight `FF` bytes, and aborts on any status other than 63CX or 6983. A stored PIN always has the §2.4.3 format, so such data never matches.
- RESET RETRY COUNTER compares the PUK before it checks the new PIN's format: yubikit blocks the PUK with `FF*8 || FF*8` and needs 63CX. A correct PUK with a malformed new PIN is 6A80 and changes nothing: the PUK counter is put back to its value before the command (two saves; a failure of the second answers 6581 and keeps the durable decrement). CHANGE REFERENCE DATA still checks the new value first (its 6A80 spends nothing); yubico-piv-tool's `ykpiv_util_block_puk` sends a well-formed new PUK, so it gets 63CX either way.
- The "explicit Le" that commands without response data reject is a non-zero Le. Le `00` (short) or `0000` (extended) is accepted with or without command data: yubico-piv-tool (`_ykpiv_transfer_data`, "Add Le for T=1") appends `00` to VERIFY, CHANGE REFERENCE DATA, RESET RETRY COUNTER, PUT DATA, IMPORT and SET MANAGEMENT KEY.
- GET METADATA for the on-card biometric comparison references `96` and `97` (SP 800-73-4 Part 1 Table 4), which only a YubiKey Bio holds, answers 6A88 (was 6A86): yubikit's `get_bio_metadata()`, called by `ykman piv info` and `PivSession.reset()`, treats only 6A88 and 6D00 as "no biometrics".
- GET DATA of an empty PIN-protected container answers 6A82 with or without the PIN (a stored one still needs the PIN, 6982): OpenSC's `card-piv.c` sets `CI_LEAKS_FILE_NOT_FOUND` for every YubiKey 4 and 5 ("GET DATA of empty object ... 6A 82 even if PIN not verified"); Part 2 §3.1.2 gives both status words without an order.
- An X25519 peer key of small order, which gives the all-zero shared secret whatever the private key (RFC 7748 §6.1), is a malformed request: 6A80 before the PIN policy and any touch, keeping the PIN-always authorization. It used to ask for a touch, spend the authorization and only then fail. Every slot request that passes the checks now completes.
- PIN and PUK reference data, the management key, slot private keys, the mutual authentication witness and the serialized record are held in `lk_crypto::SecretBytes` and wiped when dropped (`docs/DESIGN.md` §8); the record buffer is sized up front so it never reallocates.
- The PIN-always rule above matches the host software: OpenSC keeps the card locked from the context-specific VERIFY to the signature, libykpiv does not reselect before a private key operation "to avoid problems with PIN_ALWAYS", and ykman verifies again and retries a signature that answers 6982 (`_verify_pin_if_needed`).

Recorded in stage 1:

- Printed Information (5FC109) accepts PUT DATA (`reference/piv-printed-source-conflict.md`; the low-level Yubico GET/PUT DATA page); reading it needs the PIN (`pin_protected_objects_need_verified_pin`).
- Container tags are any well-formed three-byte BER tag `5F xx xx`; other tag lists are 6A80.
- GENERAL AUTHENTICATE with a P1 that is not the stored management key algorithm answers 6A86.
- A management key touch timeout answers 6982; GET RESPONSE with nothing pending answers 6985.
- GET METADATA for the management key reports PIN policy byte 00.
- Deselection and every reset kind clear PIN verification and management key authentication (a re-SELECT of PIV no longer does; see above).

Added in stage 2:

- The own F9 issuer is an ECC P-256 key, generated once when the applet is first constructed, with a self-signed CA certificate (CN `<attestation_common_name> PIV Attestation`, profile validity, basicConstraints cA) stored in 5FFF01 and charged to the object budget. It is persisted immediately (`Piv::new`); a persisted marker keeps a deleted key or certificate from being recreated.
- Attestation subject CN is `<profile product> PIV Attestation <slot>` (`YubiKey PIV Attestation 9a` under the compatibility profile, matching the documented public format). EC issuers sign with ECDSA-SHA256 (also for P-384, as documented), RSA issuers with SHA-256 PKCS #1 v1.5. Without a parsable 5FFF01, ATTEST uses the own issuer name and the profile validity.
- ATTEST of an imported key answers 6A80; of an empty slot or without an F9 key 6A88; of F9 itself, a non-key slot or P2 ≠ 00 6A86; with command data 6700. Le may be present.
- GENERAL AUTHENTICATE with the F9 key answers 6A86 (the attestation key only signs attestations); a P1 that is not the slot key's algorithm 6A86; an empty slot 6A88; malformed templates and data 6A80; missing PIN 6982; a touch timeout 6982.
- ECDSA digests may be 1 byte up to the field length (left-padded to the field length; Yubico documents "256 bits or shorter" for P-256); longer digests answer 6A80. RSA input must be exactly the modulus length and below the modulus.
- PIN policy "always": a successful VERIFY arms one operation; it is consumed when the operation is authorized, before any touch wait (a declined touch spends it). (The stage 2 rule that other commands between the VERIFY and the operation do not disarm it was replaced by the review; see above.)
- Touch policy "cached": a touch completing any slot operation successfully is remembered for 15 s (`host.now()`); a cached-policy operation inside the window needs no touch. The time survives SELECT and deselection and is cleared by every reset kind. Management key touches do not fill it.
- Default policies are resolved when a key is created (9C PIN always, 9E and F9 never, others once; touch never) and travel with MOVE; metadata reports the resolved values. PIN policies 04/05 (biometric match) answer 6A80 on the 5C Nano.
- GENERATE accepts Le (it returns data; OpenSC sends case 4); IMPORT rejects a non-zero Le with 6700 (it returns no data; Le `00` is accepted since the second review).
- MOVE onto an occupied slot answers 6985 (the Yubico SDK documents that the destination must be empty); MOVE or DELETE of an empty slot 6A88; MOVE with the same source and destination 6A86.
- RSA import requires exponent 65537 implicitly: dP, dQ and qInv must satisfy RFC 8017 §3.2 with e = 65537 (6A80 otherwise), and P and Q must give a modulus of exactly the algorithm's length.
- The F9 slot accepts only ECC P-256/P-384 and RSA-2048/3072/4096 keys (6A80 otherwise).
